Integrating NVMe-oF Storage with Domestic GPU Stacks

Published 2026-09-09 · Xinyuanyi Technology Insights

As model sizes grow and inference at scale becomes the baseline for production AI, storage performance becomes as important as GPU compute. This note explains how to integrate NVMe-oF storage acceleration into a domestic (on‑prem/local) GPU stack, with concrete evaluation criteria, an integration checklist, and an operational acceptance approach.

Why NVMe-oF matters for GPU stacks

GPUs are often starved for data when large models or many concurrent sessions read model shards, KV caches, or activation checkpoints. NVMe-over-Fabrics (NVMe-oF) lets you deliver NVMe latency and bandwidth across a datacenter fabric rather than via local disks only, enabling:

  • Lower TTFT (time-to-first-token) for large LLMs when using a remote KV cache tiering architecture.
  • Higher sustained inference throughput by avoiding NVMe device hot spots on hosts.
  • Easier scaling and easier centralized lifecycle management of all‑flash platforms.

Key design criteria and metrics to evaluate

When planning integration, measure and set targets for these metrics:

  • Latency (p50/p95/p99): critical for interactive inference and cold cache TTFT.
  • Time-to-first-token (TTFT): reflects cache warmup and initial model shard fetches.
  • Tokens/sec or inferences/sec under target concurrency.
  • GPU utilization and memory pressure: does storage latency create stalls?
  • CPU and host I/O overhead (kernel context switches, NVMe driver CPU usage).
  • Network fabric utilization (RDMA lanes, TCP offload, link saturation).
  • Failure modes and tail latency during degradations.

Quantify acceptable ranges before testing (example: TTFT reduction target, steady-state tokens/sec uplift).

Protocol and software choices

  • Transport: RDMA (RoCE/IB) typically delivers the lowest latency and CPU overhead; NVMe-oF over TCP (NVMe/TCP) simplifies deployment but has higher CPU/network cost. Choose RDMA for latency-sensitive inference.
  • Target type: NVMe-oF target exposing block devices vs. file/object stores behind an NVMe layer; block targets are lower overhead for KV cache access patterns.
  • Kernel bypass: SPDK or user-space NVMe drivers reduce CPU overhead and jitter.
  • Cache tiering: KV cache tiering (memory → local NVMe → NVMe-oF) limits remote I/O to cold misses and is the most cost-effective strategy.
  • Integrations: ensure model-serving frameworks (Triton, Ray, FastAPI + FasterTransformer/TensorRT, LangChain orchestrators) can address remote-backed filesystems or block devices safely and can prefetch or page shards.

Practical integration steps

  1. Baseline: measure current TTFT, tokens/sec, GPU/CPU utilization with models and concurrency patterns representative of production.
  2. Network readiness: validate fabric (RDMA or TCP) with microbenchmarks for latency, jitter, and packet loss under load.
  3. Storage sizing and QoS: size NVMe-oF pool and define QoS for tail latency. Plan headroom for peak concurrency.
  4. Cache tier design: define in-memory cache size (per GPU process), local NVMe eviction policy, and when to retrieve from NVMe-oF. Emphasize asynchronous prefetch when possible.
  5. Implement kernel-bypass (SPDK) or use optimized NVMe drivers on hosts running model servers.
  6. Joint test: run end-to-end tests combining the chosen GPU model, serving stack, and NVMe-oF target. Measure p99 latency, TTFT, and GPU utilization.
  7. Gate-based acceptance: accept the new storage only if it passes pre-defined gates (e.g., TTFT ≤ baseline×target, p99 within SLO). Include a stop-loss — automated rollback if errors, timeouts, or SLO breaches exceed thresholds.

Benchmarking and validation approach

  • Use representative workloads: the strongest signal comes from running your actual model (or a close surrogate) with target concurrency.
  • Collect: TTFT, tokens/sec, p50/p95/p99 latency, GPU utilization, host CPU, and network metrics.
  • Run fault-injection scenarios: simulate target node loss, network congestion, and degraded QoS to validate tail behavior.
  • Repeatability: store test configurations and raw traces so results are reproducible.

Operational considerations

  • Monitoring: add storage-level (latency, queue depth), network metrics, and application traces to correlate stalls.
  • Autoscaling: be conservative; rapid scale-outs can overload central NVMe resources.
  • Security & multi-tenancy: ensure encryption in transit and robust QoS to isolate noisy neighbors.
  • Vendor reports and reproducibility: treat signed benchmarks as a starting point; require joint, gate-based testing before rollout.

Key takeaways

  • NVMe-oF can materially reduce TTFT and raise throughput when integrated with KV cache tiering and RDMA transports.
  • Focus on workload-faithful benchmarks (TTFT, p99, tokens/sec) and joint GPU-storage testing before decisions.
  • Use gate-based acceptance with a built-in stop-loss to limit rollout risk.
  • Choose protocol (RDMA vs TCP) based on latency needs and operational capability.
